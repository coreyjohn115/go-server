# 功能文档规范

本项目要求**代码与文档同步**：任何新增功能都必须带一份对应的 Markdown 功能文档，不允许"功能先上，文档后补"。

## 核心规则

1. **同一次改动完成文档**：新增功能的代码、`doc/features/<feature>.md`、索引更新必须在同一次提交/变更中完成。
2. **一个功能一个文件**：文件放在 `doc/features/`，使用小写 kebab-case 命名，例如 `player-data.md`、`battle-room.md`、`mail-system.md`。
3. **优先更新而不是新建**：同一功能的后续修改更新原文件，并追加"变更记录"；只有新功能才新建文件。
4. **索引必须更新**：在 `doc/README.md` 的功能索引表中增加或修改一行，指向新文档。
5. **文档必须可验证**：路由号、HTTP 路径、字段名、配置项、启动顺序、预期输出必须与代码一致，示例命令应当可以直接执行（或写明前置条件）。

## 必须写文档的变更

- 新增或修改玩家可见功能（登录、背包、战斗、任务、邮件等）
- 新增路由、消息结构、HTTP 接口
- 新增 Actor、定时器、异步任务或状态机
- 新增/修改配置项、启动参数、环境变量
- 新增/修改持久化结构（MongoDB 集合与字段、Redis key、内存状态）
- 新增中间件、依赖、脚本或运维命令

## 不需要新建文档的变更

- 纯重构、重命名、格式化、注释修正（不改变行为）
- 修复 bug 且行为不变：更新对应功能文档的"变更记录"即可
- 如果确实找不到对应功能文档，说明该功能此前缺失文档：先补建再改代码

## 文档内容要求

以 `doc/features/_template.md` 为准，至少包含：

1. **功能概述**：一句话说明功能与使用场景
2. **路由与接口**：路由号/HTTP 路径、有状态还是无状态、处理进程
3. **协议示例**：请求与响应 JSON（含错误码）
4. **数据与存储**：MongoDB 集合/字段、Redis key、内存状态及其生命周期
5. **配置项**：配置位置、默认值、是否可热更新
6. **关键实现**：Actor/Task/队列、并发与落库策略
7. **运行与验证**：启动顺序、命令、预期输出
8. **变更记录**：日期 + 变更摘要

## 完成前检查

- [ ] 新功能有对应的 `doc/features/<feature>.md`
- [ ] `doc/README.md` 索引已更新
- [ ] 文档中的路由号、路径、字段、配置与代码一致
- [ ] 请求/响应示例与错误码已覆盖
- [ ] 运行与验证步骤可执行
- [ ] 若修改已有功能，旧文档已同步更新并记录变更
