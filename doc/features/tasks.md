# 玩家任务

## 功能概述

参考 Game101 的 TaskComponent、TaskEventType 和任务提交机制，实现个人成就/主线任务的接取、事件进度、完成、领奖、后续任务和持久化。

## 路由与协议

logic 有状态 + Authorized + 玩家 Actor，先登录。TCP 为 Protobuf，JSON 仅说明字段。

| 路由 | 请求 | 响应 |
| --- | --- | --- |
| 130 | TaskListReq `{}` | TaskListRes `{"code":0,"tasks":[{"id":110001,"progress":0,"target":1,"status":1}]}` |
| 131 | CommitTaskReq `{"id":110001}` | CommitTaskRes `{"code":0,"player":{...完整最新玩家快照...}}` |

status：1 接取、2 完成、3 已提交。未接取/未完成、无效配置、奖励溢出/背包满及版本冲突返回 InvalidArgument（3）和 message。失败整体回滚。已提交任务重复提交成功，不再次发奖，但仍经过 Actor 变更和落库检查。

## 配置项

`excel/Data/task.xlsx` 生成 `config/generated/tbtask.json` 和 Go 类型。执行 `gen.bat` 后重启 logic 生效，不支持热更新。

| 字段 | 含义 |
| --- | --- |
| id/name | 唯一正整数 ID、任务名 |
| taskType | 10 成就、11 主线 |
| eventType | 1 接取即完成、2 使用道具、3 获得道具、4 消耗道具 |
| itemId | 匹配道具配置 ID；0 匹配任意 |
| target | 正整数目标，进度封顶 |
| initial | 上线自动接取，已有记录不重置 |
| autoCommit | 完成自动提交发奖 |
| nextTask | 后续任务 ID；0 无后续 |
| rewardItem/rewardCount | 单种奖励；无奖励均为 0 |

默认主线：110001 使用一瓶药水，奖 100 金币并接取 110002；110002 使用三瓶药水，奖一个礼包。成就：100001 获得五个道具奖两瓶药水；100002 消耗三个道具奖 50 金币；100003 欢迎任务接取即完成、手动领一瓶药水。默认不开启自动提交，配置可开启。

启动校验重复 ID、事件类型、道具引用、奖励及后续任务缺失/环。只统计接取后事件，不回溯历史；先接取初始任务再发初始道具，初始发放计入获得。使用计入使用与消耗，删除只计入消耗。金币道具奖励计入获得，原示例 AddGold 路由不计道具事件。领奖也会触发获得事件，后续任务在奖励前接取。

## 数据与存储

MongoDB `due.players.tasks` 存储 `[{id,progress,status}]`，已提交记录永久保留以防重复发奖，target 取当前配置。无额外 Redis key。旧文档自动补齐 initial 任务；移除配置保留旧记录但禁领奖。修改目标不自动重算状态，应保持上线配置稳定或专门迁移。未实现每日重置、超时、联盟/全服任务、活动、条件命令及掉落池。

## 关键实现

只有服务端 Actor 道具事件推进进度，没有客户端任意上报进度的路由。奖励和任务状态在副本上统一校验，自动领奖连锁有配置数量上限，每个任务最多提交一次。成功后与资产在同一文档延迟保存，持久化限制见[道具系统](items.md)。

## 运行与验证

启动步骤见[道具系统](items.md)。登录后由快照或路由 120 取得药水堆栈 ID，发送路由 121 使用一瓶，然后路由 131 提交 110001，再通过 130 查看后续任务；重复提交 gold 不应再次增加。

`go test ./internal/logic/actor/player` 覆盖任务链、自动提交、重复领奖、回滚、事件和 BSON 保存恢复；`go test ./internal/common/gamedata` 检查配置。
